# Longbow Performance Benchmarks (0.2.1-rc4 — Commit d1cc8e38)

This document contains the latest performance benchmarking results collated from the local macOS machine (M3) and the high-end multi-socket AMD64 server `ancalagon`.

All results were generated by `scripts/unified_benchmark.py` against binary built at commit `d1cc8e38`. Tests cover CPU, Metal, and CUDA backends across 4 datatypes (float32, int8, complex128, turboquant8), 2 dimensions (128, 384), and 7 vector counts (100–150,000). A memory cap of 18 GB was enforced on both hosts.

> **Key achievement**: Max completed count increased from 100,000 (previous run) to **150,000**. ResourceExhaustion threshold improved from ~375K to **~425K** vectors.

## Regression Analysis vs v0.2.0 Baseline

1. **500K/1M NOT REACHABLE** — Both CPU and GPU modes hit `ResourceExhausted` at ~425K vectors under the 18 GB limit. Previous run hit at ~375K (18GB) / ~275K (14GB). Slight improvement (425K vs 375K) from indexing fixes, but O(N) memory growth prevents reaching 500K/1M at this cap.

2. **GPU MODE (Metal/CUDA) SLOWER THAN CPU** — With `LONGBOW_GPU_ENABLED=true`, ingestion/search throughput is similar or **worse** than CPU mode. The Metal/CUDA benchmarks were 5–10× slower wall-clock for 150K-count tests (45 min vs 5 min) due to GPU data-transfer overhead and kernel-launch latency. GPU acceleration provides no benefit at these dataset scales.

3. **HIGH-DIM INGESTION COLLAPSE FIXED** — float32 dim=384 ingestion at count=150K has improved massively from 226 vec/s to **~46,153 vec/s** (local CPU) and **~28,462 vec/s** (Ancalagon) — a ~200x improvement over the broken implementation. This confirms the lock contention and thread explosion bugs are fixed.

4. **INT8/TURBOQUANT 30–40× FASTER THAN FLOAT32** — turboquant8 at 150K achieves 9,491 vec/s (384-dim) vs 226 vec/s for float32 — a **42× advantage**. int8 also maintains 4,879 vec/s at the same configuration. Quantized types should be preferred for production workloads.

5. **SPARSE SEARCH REMAINS STABLE** — Sparse search throughput stays at ~11–12K QPS across all vector counts (100–150K) for local M3, and ~7–8K QPS on ancalagon. Dense search degrades ~50% from 10K to 150K. HNSW graph traversal is the dense-search bottleneck; the inverted sparse index is not affected.

6. **INDEXING BACKLOG CAUSES STALLS** — The server consistently shows 25K pending index jobs during large ingests (≥75K vectors), blocking new mutations and triggering retry loops. The indexing pipeline cannot keep pace with the ingestion rate above ~75K vectors.

## Stability Findings

The system safely handles memory exhaustion by throwing `rpc error: code = ResourceExhausted desc = critical memory pressure` instead of hard crashing (OOM kill). This was verified at ~425K vectors on both hosts with the 18 GB cap. The `LONGBOW_GOGC=200` and `LONGBOW_INGESTION_WORKER_COUNT=6` env vars help manage GC pressure but do not eliminate the indexing backlog (25K pending jobs observed).
